# 開発ワークフロー

## ブランチ運用

| ブランチ | 役割 |
|---|---|
| `main` | 正本。直接 push しない |
| `feature/<内容>` | 機能追加・画面追加 |
| `fix/<内容>` | 不具合修正 |
| `docs/<内容>` | 仕様・ドキュメントのみの変更 |
| `chore/<内容>` | 設定・CI・依存パッケージ |

`<内容>` は英小文字とハイフンで短く書く（例: `feature/score-search`）。

[要決定] 本番公開が始まったら、`develop` などの統合ブランチを挟むか決める。

## 作業の流れ

1. Issue を立てる（テンプレート: 機能追加・改善 / 不具合報告）
2. `main` から作業ブランチを切る
3. コミット → push
4. PR を作る（PR テンプレートに沿って記入）
5. CI が通り、**運営者が確認・承認してから**マージする

PR 本文に `Closes #<Issue番号>` を書くと、マージ時に Issue が自動で閉じます。

## 役割分担

- GPT: 調査・監査・要件整理・自動化
- Claude: 実装が中心
- 仕様と履歴は GitHub（`docs/` と PR）で共有する

## 人間の承認が必要な操作

AI が自動で実行してはいけない操作です。

- 本番公開・デプロイ
- ドメイン移転・DNS 変更
- 楽譜の権利ステータス（`rights_status`）の変更
- ファイルやデータの削除・大量変更
- 支払い・契約・課金処理
- 確定事項（`[確定]`）の変更

## コミット規約

`<種類>: <内容>` の形式。

| 種類 | 用途 |
|---|---|
| `feat` | 機能・画面の追加 |
| `fix` | 不具合修正 |
| `style` | 見た目のみの調整 |
| `refactor` | 動作を変えない整理 |
| `docs` | ドキュメント |
| `chore` | 設定・依存パッケージ・その他 |

例: `feat: 楽譜検索の演奏人数チップを追加`

## 秘密情報

API キー・パスワード・個人情報・本人確認書類はコミットしない。`.env` 系ファイルは `.gitignore` で除外している。
