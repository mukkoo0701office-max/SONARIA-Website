# 向山弦楽コミュニティ Discord × GitHub × ホームページ連携構想 v0.1

- ステータス: 仮置き・未実装・運営メンバーとの相談用
- 作成日: 2026-11-24
- 対象ホームページ: https://mukstrings.mints.ne.jp/
- 仮置き先: SONARIA-Website（団の本番リポジトリではない）
- 方針: まず小さく実装。通常更新にGPT/Claude APIを不要とし、定型処理をコードで実施。

## 1. 目的と優先順位

Discordへの練習日時・会場・曲目・譜面URL・備考の毎回の文字入力を減らし、既存Discordスケジュールスレッドとホームページを一度の入力から更新する。

1. 練習予定のフォーム入力と既存Discordスレッド更新
2. 練習後の実績入力（予定の再入力なし）
3. 公開可能な練習情報をGitHubに保存しHPに表示
4. 参加人数推移・曲目別練習回数などの集計グラフ
5. X公式投稿のHP埋め込み
6. 内部向け会計・議事録・運営分析への拡張

音声録音・指導要約機能は現時点では対象外。

## 2. 入力（Discord Bot）

### ① 練習前インフォメーション
- 日付、開始時間、終了時間
- 練習場所（過去の会場から選択、必要に応じ新規入力）
- 練習曲目（既存レパートリーから選択＋自由入力）
- 譜面URL（運営者が貼付、曲目別に複数URLを設定可能とする設計候補）
- 備考・連絡（自由入力）
- 作成、確認、確定、変更、中止をサポート
- 「前回の練習を複製」機能を用意

### ② 練習後の実績
- 既存の練習を一覧から選択（IDを手入力しない）
- 日時・会場・曲目は①を自動引継ぎ、変更があった項目だけ修正
- 実際の参加人数（整数）
- 会計：収入・支出（項目別、金額、備考を追加可能）
- 下書き→確認→確定。訂正は履歴を残す
- 会計は内部専用であり、公開用ファイルへ一度も書き込まない

フォームはDiscord Botのスラッシュコマンド・ボタン・セレクト・Modalを使用。Discord UIの制約に応じて複数画面に分割する。

## 3. 練習の紐づけ

日時ではなく不変の一意な `practice_id`（例 `R-0001`）を主キーとする。
- 同日に複数練習があっても別ID
- 日時や会場変更後もIDは保持
- 予定、実績、会計、HP表示、Discord反映を同じIDで対応付ける
- `status`: draft / scheduled / completed / canceled
- Discordの `thread_id` と `bot_message_id` は練習IDとは別に連携設定として管理

## 4. Discord投稿の反映先（決定：A案）

既存フォーラム投稿／スレッド **「【メイン合奏-練習スケジュール】」** を維持する。

- 運営専用の `#練習管理・bot操作`（仮称）に登録・修正ボタンを設置
- Botが既存スレッド内の**Bot自身の予定一覧メッセージ**を編集
- Botは他の利用者が書いた既存メッセージ自体は編集できない。導入時にBot投稿を新規設置する
- 投稿形式は読みやすい日付順一覧。譜面URL、連絡事項へのリンクを掲載
- 練習日変更、中止、追加時は同じメッセージを更新
- 既存スレッドのURL/IDは設置時に運営者が指定し、動作テストする
- 練習終了時は表示を「終了」に切り替えるか、過去一覧へ移動（運営と決定）

## 5. 保存とホームページ更新

```text
運営Discordフォーム
  → Discord Bot（権限・入力値検査）
  → 練習ID付きデータ保存
      ├ 公開用データのみ → GitHub → HP用JSON → ウィジェット表示
      ├ Bot投稿IDとの対応 → Discordスケジュール更新
      └ 会計・内部記録 → 非公開DB
```

- 団HPは別のメンバーが所有する既存リポジトリを利用することが本命。URLと技術構成は未確認
- 現段階は SONARIA-Website に**仕様書だけを仮置き**し、団HPへ変更を加えない
- HPへの反映は、静的JSONをサイトが読み込む方式、またはビルド/デプロイで自動更新する方式を既存構成に応じて選定
- GitHub Actionsは必要に応じて利用。必ずしも全処理に必要ではない
- 変更はプルリクエスト、レビュー、テストを通して導入
- データ更新時にClaude/GPTを毎回呼ぶ必要はない

### 公開データ例（概念）
```json
{
  "practice_id": "R-0001",
  "status": "completed",
  "date": "YYYY-MM-DD",
  "start_time": "14:00",
  "end_time": "17:00",
  "venue_public_name": "例：会場名",
  "pieces": [{"title": "曲名", "score_url": "https://example.org/score"}],
  "notes_public": "連絡事項",
  "participant_count": 16
}
```
この例の値は仕様説明用であり実活動データではない。

## 6. HPウィジェット案

1. 次回練習予定：日時、会場、曲目、譜面URL、公開可能な連絡事項
2. 最近の活動：終了した練習の日付、場所、参加人数、曲目
3. 活動統計：練習回数、延べ参加人数、練習曲数（延べ人数≠会員数）
4. 参加人数推移：練習単位・月単位の折れ線グラフ
5. 練習曲ランキング：曲目別練習回数
6. X公式タイムライン：Xの公式埋め込みを検討。環境・埋め込み仕様に依存
7. 団体紹介と参加案内：既存ページとの統一

公開値は必ず実データに基づく。ダミーデータがある場合は明示し、本番公開しない。

## 7. 公開・内部データの境界（最重要）

**絶対条件：メンバーの氏名・ハンドルネーム・Discord ID・連絡先をHPに公開しない。**
- 公開専用スキーマを使い、個人識別項目を構造上含めない
- 会計原本、個別の出欠、Discord認証情報、内部メモは公開リポジトリに置かない
- 非公開データはアクセス制御されたDBで保管
- 集計人数でも小集団の特定につながる文章は除外・確認
- 自動個人情報チェック＋運営者の公開プレビュー／承認
- URLや自由記述に個人情報が含まれないか検査
- Git履歴には削除済み情報が残り得るため、最初から秘密情報を書き込まない
- APIトークンはBot実行環境のシークレットとして管理

## 8. AIと担当分担

- ChatGPT: 企画・仕様設計・運営分析・Bot改善支援
- Claude: 初期のHPウィジェット／Bot実装支援（担当は固定しなくてもよい）
- Discord Bot: 練習予定/実績フォーム、入力検査、Discord投稿更新
- GitHub: 仕様書、プログラム、公開可能な構造化データ、変更履歴
- HP: 公開情報とグラフの表示
- 人間の運営者: 公開承認、会計確認、権限・品質の監督

ChatGPT Plusの契約はBotから直接呼び出せるAPI利用枠とは別。通常のフォーム登録・集計・HP更新にはAI APIを不要にする。

## 9. 開発ステップと受入基準

### Phase 0: 事前確認
- 団HPのGitHubリポジトリ、使用フレームワーク、デプロイ方式を担当者と確認
- Discord対象スレッドURL、Bot権限、運営ロールを確認
- 公開可能な会場名と譜面URLの扱いを決定

### Phase 1: Discord練習予定（最優先）
- 予定登録フォーム
- ID発行
- 編集／中止／前回コピー
- 既存スレッドのBot予定一覧を更新
- テスト: 追加・変更・中止後に重複投稿や他人のメッセージ改変が発生しない

### Phase 2: 実績・非公開会計
- ID選択で予定を引継ぎ
- 参加人数・項目別収支の保存
- 権限別閲覧と訂正履歴
- テスト: 公開用データに収支、氏名、IDが一切混入しない

### Phase 3: HP
- 次回練習・活動履歴・統計グラフを実データで表示
- HP担当レビューと既存サイトの表示崩れテスト
- X投稿埋込は実サイト側の対応可否で判断

### Phase 4: 拡張
- アンケート、メンバー向け出欠ボタン、予算分析、運営会議の記録、AI企画室等

## 10. 運営メンバーと相談する未決事項

- 活動データの公開承認の責任者
