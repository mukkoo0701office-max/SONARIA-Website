## 3. Jimdo PDF移行パイプライン
### 3.1 手順 [提案]
1. **Discovery**: sitemap、サイト内リンク、PDF直リンク、過去の掲載URLを収集。robots/アクセス制限/利用規約を尊重。過負荷を避け、リクエスト制限・再試行・指数バックオフ・タイムアウトを設定。
2. **Inventory**: `source_page_url`, `source_pdf_url`, `original_filename`, `discovered_at`, `http_status`, `fetch_status`, `content_type`, `byte_size` を記録。失敗理由とリトライ回数を残す。
3. **Preservation**: 元PDFを変更せず保管し、SHA-256で完全一致を検出。**同一ファイルが複数ページにある場合、元URL対応はすべて維持**。類似ファイルは機械的に統合しない。
4. **Parsing**: 作曲家・作品・作品番号・楽章・編成・パート・版・校訂者・出版社・年・原典情報を抽出。AI推定にはconfidenceと根拠を残す。
5. **Rights gate**: `unknown / needs_review / approved / rejected / withdrawn` を管理。**approved以外は一般公開しない**。公開許可の根拠・地域・確認者・確認日時を保存。
6. **Validation**: PDF破損、ページ数、向き、視認性、楽章・パート欠落、重複、版の違いを検査。最初は20〜30件のパイロットで手動照合。
7. **Publish**: 作品/版/ファイルを関連付けてページへ公開。検索インデックス更新、旧URL対応表生成、ダウンロードログ（必要最小限）記録。
8. **SEO cutover**: 301が旧ホストで可能か検証。不可なら代替移転導線を検討。公開前後で404・インデックス・トラフィックを監視。

### 3.2 ファイル名 [提案]
- 人間向けのファイル名: `composer_catalogue_movement_ensemble_part_edition.pdf`（ASCII小文字、スネークケース、固定語彙）。
- 例: `beethoven_op067_m01_orch_vn1_ed01.pdf`。
- **注意**: `ed01` は出版社/校訂版の正式識別子ではない。版を取り違えないよう、内部の `edition_id` と書誌情報で管理。
- 実ストレージの主キー: `file_id`（UUID/ULID等）＋ハッシュ。**ファイル名をIDにしない**。
- `original_filename`, `original_url`, `download_filename` を別々に保持。重複名はIDで衝突回避。日本語作品名はUIとメタデータで表現。
- 作品番号のない曲、複数作曲者、編曲者、組曲、パート分割、全集、総譜、複数版、同名作品に対応する例外ルールを作成する。

### 3.3 データモデル最小案
- `Composer(id, names_ja/en, aliases)`
- `Work(id, composer_id, titles_ja/en, catalogue_type, catalogue_value, instrumentation, slug)`
- `Movement(id, work_id, order, title)`
- `Edition(id, work_id, editor, publisher, year, source, provenance, quality_review_status)`
- `ScoreAsset(id, edition_id, movement_id?, part_code, storage_key, sha256, original_filename, mime, page_count, rights_status)`
- `SourceLink(id, asset_id, source_page_url, source_file_url, retrieval_status)`
- `RightsReview(id, asset_id, evidence, jurisdiction, reviewer, reviewed_at, decision)`
- `LegacyRedirect(old_url, new_url, redirect_type, verification_status)`
- [要検証] 作品と版の関係、複数楽章を含む1PDF、複数作品を含む1PDFは多対多の中間テーブルが必要になり得る。

## 4. 無料楽譜ページ [提案]
### 4.1 一覧
- 検索: 作曲家、作品名（日英・別名）、作品番号、編成、楽章、パート、公開権利、版。
- 絞り込みはURLに保持し、ブラウザの戻る/共有に対応。0件時に代替候補を表示。
- カード: 作品名、作曲家、編成、利用可能な譜面種類。版の品質や著作権について誤認させない。

### 4.2 作品詳細
1. パンくず→作品名/作曲家→編成/作品番号
2. 作品の短い説明・演奏上の特徴・出典
3. 楽章・版・パート切替（一覧表も用意）
4. PDFプレビュー（対応端末ではブラウザビューア、失敗時はダウンロードへフォールバック）
5. 権利/版/出典/更新日時/訂正報告
6. 独立した解説記事へのリンク・関連作品
- 作品ページは構造化データを適切に使用し、実在しない評価やレビューを生成しない。
- [提案] 楽譜検索と記事を分離。ブログ記事は編集コンテンツで、譜面データの正本にしない。
- 版の品質スコア（35/20/20/15/10）は仮指標。公開する「推奨版」は人間が確認し、判断根拠を説明。

## 5. 講師ディレクトリ（[確定]ルール＋[提案]実装）
### 5.1 不変ルール [確定]
- 登録・掲載・問い合わせ・マッチングは無料。課金掲載・優先掲載・仲介手数料なし。
- **レッスン料金・価格帯・料金検索・料金フィルタを表示/実装しない**。契約前に講師と生徒が直接料金を確認する。
- 音大在学生または卒業生のみ。ピアノ、木管、弦、金管の4分類（詳細楽器はVISION参照）。複数楽器可。
- 都道府県・最寄り駅（複数可）・指導形態・公共交通機関での約N分圏内などで検索。
- 任意の年齢表示は年代のみ。生年月日は公開しない。サイト運営者の優先表示なし。

### 5.2 フォームの段階 [提案]
1. アカウント作成: メール確認、パスワード/認証基盤、規約/プライバシー同意。
2. 資格確認: 学校・在籍/卒業状況、確認資料（**非公開・短期保持・閲覧権限限定**）。
3. 基本情報: 公開名、許諾済み写真、楽器、地域、最寄り駅、対応場所、出張起点/移動手段/分数。
4. 音楽・指導: 経歴、指導方針、対象、動画/公式SNS/サイト、年代表示の任意選択。
5. プレビュー→同意→審査申請。未入力/形式不備は明確に案内、途中保存可能。
- **公開プロフィールと本人確認情報を分離**。連絡先・学校確認書類・住所は一般公開しない。
- 入力欄はXSS/URL/ファイルタイプ・サイズ/不適切画像・個人情報露出を検査。認証・レート制限・CAPTCHA等を組み合わせる。

### 5.3 状態遷移 [提案]
`draft → submitted → under_review → approved → published`
例外: `changes_requested / rejected / suspended / withdrawn`
- 初回は管理者の資格・掲載審査後に公開。
- 公開後の通常編集は自動検証成功で即時反映。**重要情報（本人・資格・氏名等）変更は再審査**。
- 審査中も直前の承認済みプロフィールを維持し、未審査内容を公開しない。
- 全更新を監査ログ化し、公開内容の版管理・差し戻し・通報・非公開化・本人削除依頼に対応。
- 「即時反映」はアプリ上のDB更新と公開ページのキャッシュ失効を含む。検索インデックスの反映遅延には上限と監視を設定する。

### 5.4 問い合わせ [提案]
- 公開メールは出さず、仲介フォームで講師へ通知。生徒にはスパム対策・利用規約を案内。
- メッセージの保存期間、通報、返信方法、添付ファイル可否、なりすまし対策、未成年利用、個人情報削除を[要決定]。
- 検索順位は透明な関連性と更新性などに基づく。サイト運営者の優遇や有料順位操作をしない。

## 6. UI/UX・デザインシステム [提案]
- ブランド方向: 白地＋ネイビー＋ゴールド。**最終承認ロゴ画像の正本は未コミット**。近似画像で置換しない。
- 具体色（HEX）、書体、余白スケール、角丸、アイコン、ブレークポイントは実装前にデザイントークンとして確定。
- コンポーネント: Primary/Secondary/Destructiveボタン、検索、セレクト、チェックボックス、フィルタ、タブ、カード、テーブル、ページネーション、PDFビューア、アップロード、トースト、空状態、スケルトン、エラー、確認ダイアログ。
- 全コンポーネントに `default/hover/focus/disabled/loading/error/success` 状態を定義。キーボード操作、フォーカス表示、スクリーンリーダー、色コントラスト、タップ領域、モバイル操作を検証。
- Core Web Vitals、CLS（広告やPDFの領域確保）、画像最適化、キャッシュ、遅延読込を監視。動きは必要最小限で reduced-motion に対応。
- UIの「きれいさ」よりも検索成功率・登録完了率・PDF取得成功率・問い合わせ完了率を評価。

## 7. アフィリエイト配置 [確定希望＋提案]
- **[確定希望] 1ページあたり2ヶ所の広告/アフィリエイトスペースを基本とする。**
- [提案] 枠A=本文約35〜45%付近（ただし最初の主要行動を妨げない）、枠B=本文終盤・関連記事前。
- 関連性のある商品を掲載（楽譜ページ: 出版譜・教材・書籍、コラム: 参考書・音源、コミュニティ: 合奏用品など）。
- **例外**: 登録フォーム、ログイン、問い合わせ、決済、プライバシー/規約、管理画面、非常に短いページでは0〜1枠または非表示。広告2枠を強制してコンバージョン・安全性を損なわない。
- 講師ページの広告は講師推薦/ランキングと混同させない。講師登録無料・非優遇の原則を維持。
- 広告は「広告」「PR」等で明示。PDFのダウンロード/表示ボタン、フォーム送信ボタン、ナビ操作の隣に置かない。
- 未契約/広告在庫なしの場合は枠を非表示にして空白を残さない。表示時はサイズを確保してCLSを抑制。
- [要決定] 使用するASP、掲載ポリシー、Cookie/計測同意、広告の年齢・地域適合性、掲載除外カテゴリ。
- [要検証] 日本の景表法・ステマ規制、広告主規約、プライバシー法制、国外ユーザーへの同意要件。

## 8. 技術アーキテクチャ（Claudeに比較依頼）
- **決め打ちしない**。さくらインターネットの契約プラン・ランタイム・DB・バックグラウンド処理・ファイル容量/転送量・SSL・バックアップを調査してから選定。
- 候補比較軸: 静的/SSR/ハイブリッド、CMS、検索（DB全文検索/外部検索）、PDF保管（オブジェクトストレージ等）、認証、メール配送、画像変換、ジョブキュー、ログ、料金、運用負荷。
- 講師情報のDBと静的記事CMSは分離可能。資格確認書類・秘密情報は公開ストレージに置かない。
- マイグレーションとロールバック手順、開発/ステージング/本番環境、権限最小化、PRレビュー、CI、テスト、バックアップ/復旧演習を設計。
- AI/Claudeの自動実装は人間承認のPRを原則とし、秘密情報・本番公開・大量削除・課金処理は自動実行しない。

## 9. 検証・受入テスト
- **PDF**: 同一SHA256の二重登録回避、別版誤統合防止、破損PDF隔離、rights未承認の公開阻止、旧URLの対応追跡、20〜30件パイロットでメタデータを人手照合。
- **検索**: 日英別名、作品番号、楽器/パート、0件、誤字、ページング、URL共有、スマホ動作。
- **講師**: 未認証投稿拒否、初回審査前の非公開、通常編集の反映、重要変更の再審査、停止/削除、資格書類の非公開、料金フィールド不存在、スパム対策。
- **広告**: 2枠基本表示、フォーム/法務ページ除外、PR表記、ダウンロード誤クリック防止、CLS確認。
- **SEO/運用**: canonical/hreflang、sitemap、404/301、バックアップ復元、権限境界、監査ログ。
- [要決定] 数値SLO（公開反映時間、検索応答時間、可用性、復旧時間、画像/PDF容量）を設定する。
